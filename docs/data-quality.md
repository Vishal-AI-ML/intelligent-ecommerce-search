# Data Quality and Dataset Strategy

- Status: Milestone 0 design; Milestone 2 decisions recorded in §2.5, §3.1 and §5.1; Milestone 3 activated check 10 for database audits (§3.1)
- Date: 2026-09-30
- Related: `docs/spec.md`, `docs/architecture.md`

## 1. Purpose

Search metrics are only as trustworthy as the catalog and labels behind them.
This document defines how the catalog dataset is chosen and recorded, which
automated checks must pass before evaluation, and what humans must review.

## 2. Dataset selection

*Milestone 0 deliberately left the initial dataset undecided.* **Decided in Milestone 2:**
the project-authored synthetic seed catalog recorded in §2.5. The options, criteria and
provenance requirements below are kept as the original selection framework.

### 2.1 Allowed options

1. A reproducible public dataset.
2. A clearly labeled synthetic/seed catalog.
3. An allowed combination of the two, with every record's origin identifiable.

Synthetic data is never described as real marketplace data.

### 2.2 Selection criteria

- Covers the initial categories: laptops, phones, shoes, headphones.
- Contains, or can deterministically derive, the fields required by the
  schema (`docs/spec.md` FR-CAT-1/2) without inventing values.
- Supports the query types in the Golden Dataset: unconstrained,
  brand/category, specification, price, semantic intent and Hinglish.
- Has plausible prices in a single currency, or a documented currency field.
- Is small enough to ingest, embed and evaluate locally.
- Is reproducible: a fixed version, snapshot or checksum can be recorded.

### 2.3 Licensing and provenance requirements

A dataset may be used only if:

- its license or terms of use permit this use and are recorded verbatim or
  linked;
- its source, version or snapshot date, and retrieval method are recorded;
- any personal data is absent or removed before use;
- any transformation from source to catalog is scripted and repeatable;
- synthetic generation, if used, is described (method, seed or generator
  version) and every synthetic record is flagged.

If licensing cannot be confirmed, the dataset is not used.

### 2.4 Provenance record (per dataset version)

| Field | Meaning |
|---|---|
| `dataset_id` / `dataset_version` | Stable identifier and version |
| `source` | Origin (URL, publisher, or "synthetic") |
| `license` | License name and reference |
| `retrieved_at` | Retrieval or generation date |
| `checksum` | Hash of the raw input |
| `transform_version` | Version of the ingestion/normalization code |
| `synthetic` | Whether records are synthetic, per record |
| `notes` | Known gaps and caveats |

### 2.5 Milestone 2 decision (implemented)

The initial dataset is the **project-authored, deterministic synthetic seed catalog**
`synthetic-seed` version `1` (`data/seed/catalog_seed_v1.jsonl`, provenance in
`data/seed/catalog_seed_v1.provenance.json`), generated by `scripts/generate_seed_catalog.py`.

- It is **synthetic**. It is not real marketplace data and is never described as such. There is
  no third-party source, no marketplace source, no scraping and no network access. Real brand
  names are labels only; series/model names, specifications, prices, ratings and sellers are
  invented, and no affiliation with any brand or marketplace is implied.
- 240 records: 80 laptops, 60 phones, 50 shoes, 50 headphones. This is a
  correctness-oriented seed size, not a scale claim.
- Generation is deterministic (no randomness, clock or network). The committed file must
  regenerate byte-for-byte (`uv run python scripts/generate_seed_catalog.py --check`), and its
  SHA-256 is recorded in the provenance file and in `catalog_datasets.checksum_sha256`.
  `.gitattributes` pins the seed files to LF so the bytes are stable on Windows.
- Rights: a `rights_note` explains provenance. The formal `license_identifier` is nullable and is
  `null`: no licence identifier has been invented or assigned, and the repository has no
  LICENSE file.
- Templated synthetic data is easier than real listings, so retrieval metrics computed on it
  will be optimistic. About 10% of raw records use seller-style formatting variants to exercise
  normalization.

## 3. Automated quality checks

These run in Milestone 2 ingestion and must be evaluated before any search
evaluation. Each finding is reported with the product ID and the check name.

| # | Check | Intent |
|---|---|---|
| 1 | Product IDs are unique | No duplicate primary keys |
| 2 | Required fields exist | Core fields present and non-empty where required |
| 3 | Prices and numeric attributes are plausible | Non-negative prices. Numeric attributes within ranges defined per category in Milestone 2 |
| 4 | Category/attribute combinations are coherent | No attributes that do not belong to the category, such as `ram_gb` on shoes |
| 5 | Titles do not obviously contradict structured attributes | For example a title saying "16GB" when `ram_gb=8` |
| 6 | Units and storage types are recognized | Only known units and `storage_type` values. The value set depends on the storage taxonomy decision (NVMe is an interface, normally on SSDs. Milestone 6 or 7 decides how it is represented, see `docs/spec.md` §14, item 9) |
| 7 | Brand/category combinations are plausible | Against the brand dictionary |
| 8 | Duplicates do not dominate | Near-duplicate share reported. The acceptable level is set in Milestone 2 from the actual data |
| 9 | Synthetic records are identified | Every record has a synthetic flag |
| 10 | Embedding text contains no evaluation labels | Search and embedding text is built only from catalog fields |

Outcome levels:

- **Error:** blocks ingestion or evaluation.
- **Warning:** recorded and reported, record retained.

**Provisional:** which checks are errors and which are warnings is not
decided here. The examples that follow are proposals only: checks 1, 2, 9 and
10 as errors, and borderline plausibility or a suspected title contradiction
as warnings. The severity of every check is finalized in Milestone 2.

Ranges, tolerances and duplicate thresholds depend on the dataset, are
provisional, and are chosen in Milestone 2 from the selected dataset and
documented there. None are assumed here.

### 3.1 Milestone 2 implementation

Implemented in `src/ecommerce_search/catalog/quality/` and run by
`python -m ecommerce_search.catalog {ingest,check}`. A third level, **Info**, was added:
non-blocking statistics and completeness. A check that evaluated nothing is reported
`not_applicable`, never `pass`. All parameters below are **provisional engineering
guardrails, not measured marketplace facts**, are versioned as `RULES_VERSION = "1"`, and are
centralised in `catalog/quality/parameters.py` (every report embeds them).

**Severity**

| Level | Checks |
|---|---|
| Error (blocks ingestion, nothing is written) | empty catalog, schema/type validation, missing required values, invalid numbers, non-positive price, hard bounds, invalid taxonomy values, category/attribute incoherence (including cross-category attributes), NVME without SSD, inconsistent synthetic/provenance flags, duplicate product IDs, exact-content duplicates (every field identical except `product_id`), evaluation-label fields in records or schemas, missing spec linkage and raw/normalized mismatch (database audit) |
| Warning | uncommon RAM/storage, implausible ranges, price outside band, brand/category mismatch, title/attribute contradiction, same-title listings with different content, near duplicates, rating with zero reviews, missing expected attributes |
| Info | optional-field completeness, missing nullable `seller_id`, brands not in the dictionary, duplicate share, counts and distributions |

**Hard bounds (errors)**: price > 0 and <= 9999999999.99 (2 decimals); rating 0 to 5 (1
decimal); review_count 0 to 2147483647; ram_gb 1 to 4096; storage_gb 1 to 65536;
screen_size_inches > 0 to 100 (1 decimal); weight_kg > 0 to 100 (2 decimals); battery_mah 1 to
100000; battery_life_hours > 0 to 1000 (1 decimal); shoe size > 0 to 60 (1 decimal). Units:
RAM `GB`; storage `GB`/`TB` (1 TB = 1024 GB); screen `in`/`inch`/`inches`/`"`; weight `kg`;
battery `mAh`; hours `h`/`hr`/`hrs`/`hour`/`hours`. Unknown units are errors.

**Common values (warning only; an uncommon value is never rejected)**: laptop RAM {4, 8, 12,
16, 24, 32, 64}; laptop storage {128, 256, 512, 1024, 2048}; phone RAM {2, 3, 4, 6, 8, 12,
16}; phone storage {32, 64, 128, 256, 512, 1024}.

**Plausible ranges (warning)**: laptop screen 10 to 18 in, weight 0.5 to 5 kg; phone screen 4
to 8 in, battery 2000 to 10000 mAh; headphone battery life 1 to 100 h; shoe size UK 1 to 15,
US 1 to 17, EU 16 to 52.

**Price bands (warning, INR)**: laptop 10000 to 500000; phone 3000 to 250000; shoes 300 to
30000; headphones 200 to 60000. A non-INR currency is a warning and its band is not assessed.

**Duplicates** (deterministic; limitations stated):

* *Exact-content duplicate (error):* two different `product_id`s whose normalized content is
  identical in every other field, seller included. Nothing distinguishes the listings, so the
  identity is contradictory.
* *Same-title listing (warning):* same category, brand and case/whitespace-normalized title but
  different content (another seller, price, rating, ...). Legitimate multi-seller listings look
  like this, so it never blocks ingestion. Different brands or categories are never grouped.
* *Near duplicate (warning):* title token-set Jaccard >= 0.9 (inclusive) within the same
  category and brand (tokens are casefolded `[a-z0-9]+`).
* *Limitations:* the rules compare normalized text and fields only. They cannot recognise the
  same product described with different words, and a re-listing that differs in a single field
  (for example the rating) is a warning, not an error. Near-duplicate detection is
  O(n^2) per brand/category group.

**Empty catalogs**: a catalog with no records is an error (`catalog_non_empty`, status `fail`),
distinct from `not_applicable`. This applies to files (even when the provenance claims zero
records) and to a database audit with zero products.

**Title contradictions (warning)**: only explicit `N GB RAM`, `N GB|TB SSD|HDD|NVMe|storage`
patterns and the words wireless/wired/noise cancel and men/women/unisex/kids are compared;
nothing is inferred. The brand must appear in the title.

**Check 10 (embedding/search text contains no evaluation labels).** Not applicable in
Milestone 2 (no search text existed). **Milestone 3 activates it for database audits only**
(`catalog check --database NAME`, check name `embedding_search_text_leakage`). File-side
reports keep it `not_applicable` (search documents are derived rows that exist only in a
database). A database audit rebuilds every product's search vector from the stored catalog rows
with the same builder used by ingestion and compares it with the stored vector, and reports an
error for: a **missing** document, a **stale** `document_version`, a **source content hash**
that differs from `products.content_sha256`, a **tampered or unexpected** vector (any difference
from the rebuilt one), and unexpected lexemes that match review, evaluation or provenance text
(`catalog_reviews` verdicts/issue fields/notes, dataset ids, source-type markers). A database not
migrated to `0003` reports the check as `not_applicable` with that reason. The audit does not
decide whether text is a "label" by word: the bare word "synthetic" is legitimate catalog text
(a shoe material in the seed), so the guarantee is structural (the builder reads a closed
whitelist of fields; a unit test enforces it) plus rebuilt-vector equality. Database quality reports also carry a clearly separate `search_index` section (not the M2
`versions` block): `document_version`, `fts_config`, `search_version`, the number of products and
search documents, and the counts of missing documents, stale document versions, source-hash
mismatches and tampered or unexpected vectors. File reports state in the same section that the
audit is not applicable because no stored search index exists. **`RULES_VERSION`
stays `"1"`:** the search index has its own versioning (`DOCUMENT_VERSION`), and bumping the rule
set would make ingestion refuse to re-ingest existing dataset versions (an M2-tested guard).
Structural separation is also covered by `schema_no_label_fields` and
`evaluation_label_fields`.

## 4. Raw data preservation

- Raw input is stored exactly as received, separately from normalized
  values.
- Normalization is deterministic, versioned and repeatable from raw.
- Inferred values (model decisions) are stored separately, with provider,
  model version and confidence.
- Nothing overwrites raw seller data.

## 5. Human review

- At least 30 representative products are prepared for **real human
  review** in Milestone 2, covering every category and a range of quality
  findings.
- Review completion is recorded only by a human. It is never marked complete
  automatically, and no reviewed labels are generated.
- Golden Dataset relevance labels (`relevant`, `borderline`,
  `not relevant`) and decision-evaluation labels are human-produced.
  Model-generated labels may be used only as unverified suggestions and are
  never authoritative.
- Search annotation is done in the Milestone 9 annotation tool, whose
  requirements are in `docs/spec.md` §6.7. Gold constraints used for
  Constraint Satisfaction Rate are also human-annotated
  (`docs/spec.md` §9.2).
- Until the Golden Dataset exists, any queries used in Milestones 3 to 8 are
  provisional smoke queries. They carry no authoritative labels
  (`docs/spec.md` §9.1).

### 5.1 Milestone 2 review workflow (implemented; review recorded 36/36)

`python -m ecommerce_search.catalog review-sample` writes a deterministic 36-product sample
(10 laptops, 10 phones, 8 shoes, 8 headphones) to `data/processed/catalog_review/`
(git-ignored): `review_sample.csv`, `review_manifest.json` and instructions. Selection per
category is: products with warnings first (up to half the quota), then one product per brand,
then fill, all ordered by SHA-256 of a fixed seed and the product ID. Every verdict field is
left blank. A human fills `verdict` (`accept`, `needs_correction`, `unsure`) for **every** row
and records it with `review-import --database <name> --reviewer <handle>
--confirm-human-review`. Only the three reviewer columns may be edited: the manifest binds each
sampled product's `content_sha256` and a hash of every non-review CSV column, and import is
refused if any of them changed. Before recording, the live product's `content_sha256` must still
equal the reviewed value (a product changed after sampling is refused). Rows go to the
append-only `catalog_reviews` table (UPDATE/DELETE/TRUNCATE are blocked by triggers), which also
stores `product_content_sha256` and the manifest hash. `review-sample` never overwrites existing
files and never a CSV with reviewer input.

**Durable evidence.** Before recording anything, `review-import` requires the supplied
manifest to equal exactly the review sample generated by the committed seed and the current
sampling code (a hand-crafted manifest is refused even when its internal hash is
self-consistent; nothing is written to the database or `data/labels/` on refusal). It then
writes `data/labels/catalog_review_<dataset>_v<version>_<batch>.json` (evidence schema version
2): `schema_version`, `review_batch_id`, `manifest_sha256`, dataset id/version/checksum,
**`manifest`** (the exact reviewed manifest, schema version 3: seed, selection version and
method, quotas, rules/taxonomy/transform versions, and every sampled product's `product_id`,
`content_sha256` and non-review `row_sha256`), `reviewer_handle` (a handle, never an email),
`recorded_at` (UTC), `product_count`, one entry per sampled product (`product_id`,
`product_content_sha256`, `verdict`, `issue_fields`, `notes`) and a canonical `records_sha256`
self-hash.

*Historical verification* (`review-verify`, `review-status`; offline, no database) uses only the
evidence file and the committed seed: it validates the embedded manifest's schema, recomputes
its digest and batch id, checks the top-level copies against it, requires at least 30 unique
products with exactly one outcome per embedded product in the embedded order (no missing, extra,
duplicated or reordered entries), checks every product content hash and the dataset
id/version/checksum against the committed seed, and verifies the evidence self-hash. It does
**not** consult the current rules version, selection wording, quotas, sample seed or row
rendering, so later changes to those never turn valid historical evidence into `ERROR`.
Whether today's sampling code would still reproduce the reviewed manifest is reported only as
the informational `matches_current_sampling_rules` line. Row hashes are historical rendering
facts: they are protected by the manifest digest and the self-hash but are not re-derived from
current code. Evidence is found by dataset id and version, so renaming constants never hides
it. `review-status` reports `PENDING` when no file exists, `RECORDED 36/36` when it verifies,
and `ERROR` (exit 1) otherwise (including when more than one evidence file matches). The
optional `--database` cross-check reads the append-only table using the embedded reviewed
manifest and is advisory; the evidence file is authoritative. Notes must contain no personal
information. Git history plus a reviewer handle are an **audit trail and integrity check, not
cryptographic proof** of identity. The evidence file is committed only after a real human
review. No tool fills in or imports a verdict automatically. This is not the Milestone 9
annotation tool.

**Status rules.** A batch is `RECORDED` only if every manifest product has exactly one outcome
from a single reviewer, with matching manifest hash, dataset/checksum and product content hash,
and no product outside the sample. Partial clean batches are `PENDING`; mixed reviewers, foreign
products, wrong hashes or duplicates are `ERROR`.

**Recorded review (Milestone 2).** The representative human review is recorded: **36/36**
products (10 laptops, 10 phones, 8 shoes, 8 headphones), reviewer handle `Vishal`, all 36
verdicts `accept` (0 `needs_correction`, 0 `unsure`). Durable evidence:
`data/labels/catalog_review_synthetic-seed_v1_c90b5cd0a3a7.json`,
file SHA-256 `302d725dcf399679977f55a3da98976aa499c003a5236a1772eae42b368e9265` (the hash of the file as written with LF line endings; verification uses
the line-ending-independent canonical `records_sha256` inside the file). Offline `review-verify`
and `review-status` succeeded without a database. The review is bound to the exact dataset
checksum, the embedded reviewed manifest and every product's `content_sha256`. It is an
integrity/audit artifact: Git history supplies attribution, and it is **not cryptographic proof
of the reviewer's identity**. The catalog is synthetic and internally coherent; the review does
not establish real-market availability, pricing or product existence.

**Limitation of the real sample.** The synthetic seed currently produces zero warnings.
Warnings-first selection is implemented and unit-tested with injected findings, so the real
36-product sample is stratified by category and brand rather than by actual warning types. No
defects are invented to make the sample look diverse.

## 6. Evaluation leakage controls

- Golden queries and labels live under `evals/`, separate from catalog data.
- Embedding text and FTS text never include labels or query-specific hints.
- Tuning versus reporting leakage: a configuration tuned on the queries used
  for final reporting gives optimistic metrics. Authoritative reports must use
  a recorded tuning/reporting split, use cross-validation, or explicitly
  disclose that the configuration was tuned on the reporting set. The
  preferred approach is to freeze the primary configuration before final
  reporting (`docs/spec.md` §9.3).
- Candidate-pool bias in pooled Recall@K is disclosed in reports
  (`docs/spec.md` §9.2).

## 7. Versioning

Catalog version, dataset version, golden-set version and normalization-rule
version are recorded in every experiment. Changing any of them requires
regenerating dependent artifacts (such as embeddings) and rerunning
evaluation.
